# ADR-002: Test-Driven Development

## Status
Accepted

## Date
2026-06-27

## Context

This project uses AI coding agents (via spec-kit) to implement features from specs and plans. Without an explicit methodology constraint, AI agents default to writing implementation first and tests after — or skipping tests entirely. This produces code that is hard to verify, easy to break silently, and that treats tests as documentation rather than design tools.

TDD is enforced as a non-negotiable process rule so that tests define the contract before any implementation exists, regardless of whether the author is human or AI.

## Decision

All implementation on this project follows strict red-green-refactor TDD:

1. **Red** — write a failing test that describes one unit of behaviour. Run it. Confirm it fails for the right reason.
2. **Green** — write the minimum code to make the test pass. No more.
3. **Refactor** — clean up the implementation without changing behaviour. Tests must still pass.

Repeat for each unit of behaviour.

### Scope

TDD applies to all layers:

| Layer | Test tooling | What to test |
|---|---|---|
| Rust (backend) | `#[cfg(test)]` + `#[test]`, `tokio::test` for async | executor logic, command handlers, package injection, validation |
| Svelte components | Vitest + `@testing-library/svelte` | user interactions, rendered output, state changes visible in the DOM |
| State / model | Vitest | state actions, derived values, edge cases |
| Shared utilities | Vitest | pure functions, Zod schemas |

Integration tests (frontend invoking real Tauri commands) are out of scope for the TDD cycle but are encouraged where practical.

### Rules for AI agents

When implementing any task from `tasks.md`, an AI agent MUST:

1. **Write the test file first.** The test file must exist and the test must be runnable (and failing) before any implementation file is created or modified.
2. **Run the test and confirm it fails.** Do not proceed to implementation without seeing a red result. If the test passes without implementation, the test is wrong — fix it.
3. **Implement only what is needed to pass the test.** Do not write code that is not required by a currently failing test.
4. **Run the full test suite before marking a task done.** No regressions are acceptable.
5. **Never delete or skip a test to make the suite pass.**

### Test file location

- Frontend: colocated with the source file (`Button.test.ts` next to `Button.svelte`)
- Rust: inline in the same file under `#[cfg(test)]` or in `src/tests/` for integration-level tests

### What counts as a unit

- One Rust function or command handler = one test module with multiple `#[test]` cases
- One Svelte component = one test file covering its public behaviour (props in, DOM/events out)
- One state action = one `it()` block per behaviour branch

### What does not require TDD

- Build scripts and compile-time tooling (esbuild bundling, `include_str!` embedding)
- CSS and visual styling
- Wiring and composition (e.g. mounting a widget in the layout) — covered by the component's own tests

## Consequences

**Positive:**
- Every piece of logic has a test that existed before the implementation — regressions are caught immediately
- AI agents cannot ship untested code without explicitly violating this ADR
- Tests serve as living documentation of intended behaviour, not an afterthought
- Refactoring is safe at any point — the test suite defines the contract

**Negative:**
- Slower initial implementation — each behaviour unit requires a write-run-fail cycle before code is written
- AI agents must have access to a test runner in their execution environment to confirm red/green states
- Trivial wiring code (mounting components, registering commands) feels over-constrained by TDD — exemptions above exist for this reason
